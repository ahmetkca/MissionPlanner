# 0003. MCP server supports both stdio and Streamable HTTP

- **Status:** Accepted
- **Date:** 2026-04-15

## Context

The Model Context Protocol specifies two transports an MCP server can expose:

- **stdio**: the agent (e.g., Claude Code) spawns the server as a child process and exchanges JSON-RPC messages over stdin/stdout. One server instance per agent session. Terminates when the parent agent exits.
- **Streamable HTTP**: the server runs as a long-lived process, binds an HTTP endpoint (by convention `/mcp`), and accepts session-scoped connections from multiple agents concurrently. Sessions are identified by a `Mcp-Session-Id` header generated by the server.

MCP clients in the wild vary in what they support. Claude Code supports both but documents stdio as the common path. `@modelcontextprotocol/inspector`, the official debugging tool, speaks HTTP. Some editor plugins and orchestration frameworks prefer HTTP because it lets them reuse a warmed-up process across sessions.

Supporting only stdio is the simplest choice and sufficient for the headline use case (Claude Code talking to a local MP install). Supporting only HTTP is a non-starter because every agent launch would need to race a server startup. The question is whether to pay the cost of supporting both.

## Decision

**The MCP server ships with both transports in a single binary**, selected at startup via a `--transport <stdio|http>` CLI flag. stdio is the default and documented as the primary path; HTTP is available for debugging and advanced use.

Concretely:

- Entry point at `src/index.ts` parses `--transport`, `--port`, and `--bridge-url` from `process.argv` and dispatches to one of two branches.
- stdio branch: constructs `StdioServerTransport` from `@modelcontextprotocol/sdk/server/stdio.js`, calls `server.connect(transport)`, and returns. The process stays alive as long as the parent agent holds the stdio pipes open. Exits with the parent.
- HTTP branch: constructs `StreamableHTTPServerTransport` with `sessionIdGenerator: () => randomUUID()`, creates a Node `http.Server` bound to `127.0.0.1:<port>`, and routes requests: `/mcp` and `/mcp?...` go to `transport.handleRequest(req, res)`; `/health` returns `{"status": "ok"}` for liveness checks; everything else returns 404. `SIGINT` and `SIGTERM` trigger graceful shutdown (`httpServer.close()` then `server.close()` then `process.exit(0)`).
- The same `McpServer` instance (tools + resources, built by `createServer()`) is used in both branches. Transport selection is the only fork in the code path.
- Default HTTP port is `9990` — deliberately one digit off from the bridge's `9999` so it's hard to confuse at a glance but easy to remember as a pair.

## Consequences

**Positive:**

- **Zero-config default for Claude Code users.** `npx --yes @ahmetkca/missionplanner-mcp-server` with no flags does the right thing: stdio, spawned by the agent, one-per-session, no ports to configure. This is what the README's install snippet uses.
- **Debugging has a real answer.** Connecting `@modelcontextprotocol/inspector` to a running server requires HTTP. Without the HTTP mode, every bug report would require either reproducing in the agent UI or building a custom stdio harness. With HTTP mode: `npm run start:http` and point the inspector at `http://127.0.0.1:9990/mcp`.
- **Shared warmed-up process across agent sessions.** A single HTTP-mode server can serve multiple Claude Code / other-agent sessions without paying startup latency each time. The bridge compatibility check and SDK init happen once.
- **Liveness probes are trivial.** `/health` lets any watchdog (systemd, PM2, Docker healthchecks) verify the process is responsive without speaking MCP.

**Negative:**

- **Two code paths to maintain.** Transport-specific bugs can happen in one branch and not the other. The shared `McpServer` instance mitigates this — the actual tool logic is identical — but transport setup, shutdown semantics, and error reporting differ.
- **HTTP mode is localhost-only and has no auth.** `httpServer.listen(port, "127.0.0.1", ...)` binds loopback only, but there is still no authentication. Running HTTP mode on a shared machine means any local process can send tool calls. This is consistent with the bridge (also loopback, also no auth) and is documented as a pre-1.0 constraint.
- **Session lifecycle is looser in HTTP mode.** stdio has a natural "parent exits, I exit" lifecycle. HTTP mode keeps sessions in memory until the transport GCs them. For an MVP with a single user on a local machine this is fine, but it is a different failure mode — sessions can leak if a client disconnects uncleanly.
- **Windows install quirks only matter in stdio mode.** The `cmd /c npx --yes` wrapper, the `--yes` flag, and the `#!/usr/bin/env node` shebang are all workarounds for `npx` behavior when an agent spawns the server as a child. HTTP mode sidesteps them entirely — the user runs `npx` themselves, so `PATHEXT`, shim generation, and the first-run prompt are all handled interactively.

**Neutral:**

- The flag surface is minimal: `--transport`, `--port`, `--bridge-url`. Adding a third transport (SSE, WebSocket, etc.) means adding a case to the dispatcher, not redesigning the entry point. The shape scales.

## Alternatives considered

**stdio only.** Rejected because it leaves no supported path for `@modelcontextprotocol/inspector` or any other HTTP-native client. Debugging would require writing a custom stdio tester or waiting to reproduce issues in the target agent. The cost of HTTP support is one extra branch in `main()`, which is not a meaningful maintenance burden given the SDK provides `StreamableHTTPServerTransport` as a drop-in.

**HTTP only.** Rejected because it forces every user to run a separate long-lived process before their agent works. The agent-spawn model is what every out-of-the-box Claude Code user expects, and requiring a background process before the agent is useful would be a significant adoption barrier. It would also mean the install story is "install the package, then figure out how to run it persistently" rather than a single `mcpServers` JSON block.

**Two separate packages (one per transport).** Rejected because the actual server logic — tool handlers, resource handlers, bridge client — is 100% shared. Splitting into two packages would mean either duplicating the code (maintenance drift) or adding a third "core" package with versioning across three artifacts. A single package with a `--transport` flag is strictly simpler.
